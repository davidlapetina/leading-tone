# Architecture

## What it is for

> Keep an accurate model of what someone knows about music theory, and continuously teach
> them the right next thing — through conversation, notation and the piano — without
> following a predetermined course.

Everything here serves that. Anything that does not is not here.

## The loop

```
learner
   │
   ▼
LearnerService.snapshot()          what do we currently believe?
   │
   ▼
TeachingPolicy.next()              what is the right thing to do about it?      [deterministic]
   │
   ▼
ExerciseGenerator.generate()       build the question and its answer key        [deterministic]
   │
   ▼
TutorModel.respond()               put it into a teacher's words                [language model]
   │
   ▼
learner answers, in words or at the keyboard
   │
   ▼
ExerciseEvaluator / MidiEvaluator  is it right, and if not, how is it wrong?    [deterministic]
   │
   ▼
EvidenceService.record()           append the evidence, recompute mastery       [deterministic]
   │
   └──────────────► back to the top
```

By the time the language model is called, every decision that matters has been made. The
model supplies the words and nothing else.

## What the model may and may not do

| | |
|---|---|
| **May** | explain, question, use analogies, choose an example, respond to confusion, interpret free-form answers, propose evidence |
| **May not** | choose the concept, choose the pedagogical action, set the difficulty, decide whether an answer is right, write a mastery value, declare anything mastered |

The enforcement is structural rather than a matter of prompt discipline. `LearnerTools`
exposes `proposeEvidence` and there is no `setMastery` to call. A proposal is recorded at
`EvidenceService.MODEL_JUDGED_CONFIDENCE` (0.6), which caps how far a model's opinion can
move the learner model however sure it sounds.

That cap is not enough on its own, because the learner's own words reach the prompt and
can talk a model into calling a tool. `TurnScope` fences the one tool that writes:

- one proposal per turn, and no more;
- only about the concept currently being taught;
- only of a kind the model could have witnessed — it may report what someone *said*, never
  what they *played*.

Refused proposals return an explanation to the model rather than an error, so it can carry
on teaching.

## Facts, not recall

The model is also not trusted to remember theory correctly. `TheoryBriefing` computes the
facts for the concept in hand — the spelling of Cmaj7 against C7, the figures for each
inversion, the diatonic triads of the key — and puts them in the prompt. Asked about a "C
major add 7" without it, a model answered "C, E, G and B♭", which is a different chord.

Published prose sits **below** those computed facts in the prompt and is fenced as
quotation, and the prompt says which wins: if a retrieved passage disagrees with the
engine, the engine is right. The two are different classes of claim. A briefing is produced
by the same code that marks the learner's answers; a quotation is somebody else's writing,
worth citing and not worth trusting over arithmetic.

Fencing retrieved text is mitigation, not proof, and the doc should not overclaim. What
actually protects the learner is unchanged by retrieval: the model cannot write mastery,
choose the concept, set the difficulty or mark an answer. **Retrieval adds no new write
path.**

Everything in the briefing is generated by the same engine that marks the answers, so the
two cannot drift apart.

## Packages

```
fr.lapetina.music
├── theory          spelled pitch, intervals, scales, keys, chords, Roman numerals,
│                   progression analysis, ABC notation. No CDI, no persistence, no I/O.
├── concept         the prerequisite graph, loaded from concepts.json
├── learner         the learner model: evidence, mastery, review schedule, misconceptions
├── tutor           the policy, the session, and the orchestrator that runs the loop
├── exercise        generation and evaluation of exercises
├── midi            evaluation of what was actually played
├── llm             the language model behind an interface, its prompt, and its tools
├── theoryservice   the CDI façade onto theory, kept outside it so theory stays
│                   framework-free — there is a test that enforces this
├── knowledge       published sources: the registry, licensing, ingestion, chunking,
│                   in-process embeddings, the Lucene index, retrieval, attribution,
│                   and the harmony corpora with their engraved excerpts
└── api             REST resources and their read models
```

The dependency direction is inward: `theory` knows about nothing, `learner` knows about
`concept`, `tutor` knows about everything below it, and `api` knows about `tutor`.
`knowledge` depends only on `theory` and `concept`, so both it and `llm` can be deleted and
the application still teaches — with computed facts and generated exercises, just without
citations. The
`llm` package can be deleted and the application still teaches — less pleasantly, but
correctly. See `TemplateTutor`.

## Why the theory engine is written in Java rather than delegated

A tutor that cannot tell a first inversion from a root position cannot teach inversions.
Every claim the tutor makes about music is computed: `ChordAnalyzer` identifies what was
played, `ProgressionAnalyzer` labels it in a key, and both are covered by tests that state
musical facts rather than implementation details.

This is also what makes the feedback teachable. The evaluator does not return "wrong"; it
returns *correct notes, wrong bass*, which is the difference between

> Wrong.

and

> The right notes, but the bass should be B and you played G at the bottom.

## Data

Flyway owns the schema (`V1__initial_schema.sql`); Hibernate is set to `validate`, so a
mapping that drifts from the schema fails at boot rather than at runtime.

`evidence` is append-only. Every mastery value in the application can be traced back to
the rows that produced it, including the mastery before and after each observation. That
audit trail is the reason to trust the tutor's claims — and the reason it can be argued
with.

## When the model is not there

A local model does not fail fast. It waits out its timeout, the client retries once, and a
single turn can block for minutes. Paying that on every turn makes the application
unusable, so `FailureWindow` stops calling a model that has just failed and serves
template turns immediately for a cooldown period. `GET /api/session/status` reports which
narrator is answering and why.

Nothing about a model failure touches the learner model. Mastery only ever moves through
`EvidenceService`, from a deterministic verdict.

## Ports

The backend listens on **8088** and Postgres on **5433**, both off their usual defaults so
this stack can run beside another one. Override with `MUSIC_HTTP_PORT` and `MUSIC_DB_PORT`.

## One learner, one identity

The application teaches one person, and that person has a fixed primary key
(`Learner.SINGLETON_ID`). Find-or-create run concurrently produces two learners, after
which the interface reads one and writes to the other; a React effect running twice on
mount was enough to do it. The learner is seeded at startup and the request path only
reads.
